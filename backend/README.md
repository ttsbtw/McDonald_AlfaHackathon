# Backend: вход, продукты, черновики и отправка заявок

Реализация задачи #2: FastAPI, SQLAlchemy 2, PostgreSQL и Alembic, без стороннего
шаблона. Выбор согласован 21.10.2026. Python 3.12.15; точные версии Python-пакетов
и их хеши закреплены в `requirements*.txt`.

Доступны вход действующего клиента/сотрудника, сведения о своей компании,
каталог продуктов, работа с черновиками, история заявки и отправка полной
анкеты. При отправке backend запускает локальные симуляторы, вызывает модуль
скоринга, сохраняет снимок входа и результат оценки и переводит заявку в `UNDER_REVIEW`.
Сотруднику доступны фильтрованная очередь, карточка заявки, история оценок,
запрос уточнений, одобрение и отказ с сохранением действий и комментариев.

## Запуск через Docker Compose

Нужны Docker Engine/Desktop и Compose v2. Все команды выполняются из корня
репозитория. Для первого запуска скопируйте `.env.example` в `.env` (не затирайте
существующую конфигурацию) и заполните `JWT_SECRET` случайной строкой:

```sh
cp .env.example .env
python3 -c "import secrets; print(secrets.token_hex(32))"
```

Вставьте полученное значение в `JWT_SECRET=`. `.env` исключён из Git и не
попадает в Docker-образ. Пример содержит публичные **демонстрационные** пароли;
это локальное окружение с синтетическими данными. Для пароля PostgreSQL в этой
Compose-конфигурации используйте URL-безопасные символы: буквы, цифры, `_`, `-`.

```sh
docker compose up --build -d
docker compose ps
```

Compose запускает PostgreSQL, ждёт его готовности, применяет миграции, при
`SEED_DEMO=true` создаёт демоданные и запускает API.

- Swagger: http://localhost:8000/docs
- OpenAPI: http://localhost:8000/openapi.json
- Проверка процесса: http://localhost:8000/health
- Готовность БД и миграций: http://localhost:8000/ready

Backend опубликован только на `127.0.0.1`; порт PostgreSQL наружу не открыт.
Данные находятся в именованном томе `postgres_data`. Для обычной остановки:

```sh
docker compose down
docker compose up -d
```

**Не добавляйте `-v` к `down`, если нужно сохранить данные:** этот флаг удаляет том.
Обычный перезапуск приложения: `docker compose restart backend`.
Повторное заполнение демоданными не сбрасывает пароли, продукты или заявки.
Смена переменных DEMO_* после первого запуска также не меняет существующие пароли.

## Демонстрационные учётные записи

| Логин | Роль | Переменная пароля | Пароль из .env.example |
| --- | --- | --- | --- |
| `client1` | CLIENT | DEMO_CLIENT_PASSWORD | `Client-one-demo-2026!` |
| `client2` | CLIENT | DEMO_SECOND_CLIENT_PASSWORD | `Client-two-demo-2026!` |
| `employee` | BANK_EMPLOYEE | DEMO_EMPLOYEE_PASSWORD | `Employee-demo-2026!` |

У клиентов разные компании. ИНН начинаются с нулей и намеренно являются
синтетическими идентификаторами, не проверенными реквизитами реальных компаний.
Пароли хранятся как Argon2-хеши. Токен подписывается HS256, действует 30 минут;
при каждом запросе активность пользователя и роль проверяются в БД.
Сотрудник может входить и читать продукты и заявки, переданные на рассмотрение.
Доступ к клиентским операциям черновиков закрыт.

## Проверка через Swagger

1. Откройте `/docs`, нажмите **Authorize**, введите `client1` и его пароль.
   `client_id` и `client_secret` оставьте пустыми. Используется password-form
   входа; сервер возвращает Bearer-токен. Либо вызовите `/api/v1/auth/login`
   с `application/x-www-form-urlencoded`.
2. Вызовите `GET /api/v1/company` и `GET /api/v1/products`.
3. В `POST /api/v1/applications` отправьте `{}` или частичную анкету:

```json
{
  "product_code": "working_capital",
  "requested_amount": "300000.00",
  "term_months": 12,
  "purpose": "Закупка материалов"
}
```

4. Сохраните `id` и `revision` ответа. Для дополнения используйте
   `PATCH /api/v1/applications/{id}`:

```json
{
  "revision": 1,
  "average_monthly_revenue": "1000000.00",
  "average_monthly_operating_expenses": "600000.00",
  "existing_monthly_debt_payment": "50000.00"
}
```

5. Выполните `docker compose restart backend`, войдите снова и получите заявку
   через `GET /api/v1/applications/{id}`. Поля и версия должны сохраниться.
6. Выйдите через **Authorize → Logout**, войдите как `client2`: GET и PATCH
   по сохранённому чужому `id` должны вернуть **404**, а свой список — быть пустым.
7. Попробуйте PATCH со старой `revision`: получите **409**, предыдущие изменения
   сохранятся. Попытка передать `owner_id`, `company_id`, `status` или `score`
   в клиентском запросе даст **422**.
8. Для полной анкеты вызовите `POST /api/v1/applications/{id}/submit` без тела.
   Неполная анкета вернёт **422** с перечнем обязательных полей. Успешная отправка
   сохранит оценку и переведёт заявку в `UNDER_REVIEW`; повтор запроса безопасен.

Дополнительные запросы: [examples/requests.http](examples/requests.http).
Зафиксированная схема: [docs/openapi.json](docs/openapi.json).

## API и контракт со скорингом

| Метод | Путь | Доступ |
| --- | --- | --- |
| POST | `/api/v1/auth/login` | Без токена; форма username/password |
| GET | `/api/v1/auth/me` | Любая действующая учётная запись |
| GET | `/api/v1/company` | Своя компания клиента |
| GET | `/api/v1/products` | Активные продукты; клиент и сотрудник |
| GET | `/api/v1/products/{code}` | Активный продукт; клиент и сотрудник |
| POST | `/api/v1/applications` | Новый свой черновик |
| GET | `/api/v1/applications` | Свои заявки; limit 1–100, offset >=0 |
| GET | `/api/v1/applications/{id}` | Своя заявка |
| GET | `/api/v1/applications/{id}/events` | История правок и переходов своей заявки |
| PATCH | `/api/v1/applications/{id}` | Своя заявка в DRAFT/NEEDS_INFO, с revision |
| POST | `/api/v1/applications/{id}/submit` | Полнота анкеты, локальные проверки, скоринг и передача в рассмотрение |
| GET | `/api/v1/bank/applications` | Очередь сотрудника; фильтр по статусу, limit 1–100, offset >=0 |
| GET | `/api/v1/bank/applications/{id}` | Карточка заявки с клиентом, компанией, продуктом и последней оценкой |
| GET | `/api/v1/bank/applications/{id}/assessments` | Все оценки заявки, от новой к старой |
| POST | `/api/v1/bank/applications/{id}/request-info` | Запрос уточнения с обязательным комментарием |
| POST | `/api/v1/bank/applications/{id}/decision` | Одобрение или отказ по текущей оценке |

При создании все поля анкеты необязательны: `product_code`, `requested_amount`,
`term_months`, `purpose`, `average_monthly_revenue`,
`average_monthly_operating_expenses`, `existing_monthly_debt_payment`.
Пропуск или null — неизвестное значение. При PATCH пропущенный ключ сохраняет
старое значение, явный null очищает его. Пустая строка не заменяет null.

Деньги — строки, RUB, до двух знаков после точки, максимум 1 трлн; `float` и
числовой JSON не принимаются. Запрашиваемая сумма положительная, остальные
суммы неотрицательные. Срок — целое 1–360. В черновике можно временно сохранить
параметры вне диапазона продукта; при отправке правила скоринга сохраняют это
как причину рекомендации, а не блокируют сохранение черновика. Неизвестный/
неактивный продукт выбрать нельзя.

Выручка и расходы — средние за один период: последние 12 завершённых месяцев,
для молодого бизнеса — доступные завершённые месяцы. Расходы не включают выплаты
по кредитам. API сохраняет заявленные средние, но не проверяет документы.

Согласованный способ подготовки входа скоринга:

- Финансовые поля, продукт, цель, сумма и срок берутся из заявки без переименования.
- `application_id` = id заявки, `application_revision` = revision.
- `legal_form` и `registration_date` берутся из компании.
- `schema_version` = `1.0`, `as_of_date` задаёт backend в момент отправки.
- Политика берётся из `credit_products.scoring_policy` на сервере.
- `current_overdue_amount`, `max_overdue_days_12m` и checks задают локальные
  детерминированные симуляторы; клиент их не задаёт.

Создание, изменение полей и отправка добавляют запись в `application_events`
в одной транзакции с изменением заявки. `GET /api/v1/applications/{id}/events`
возвращает события только владельцу, включая редакцию анкеты и переход статуса.
Запрос уточнений добавляет событие и сообщение клиенту; после исправлений
повторная отправка создаёт новую оценку, не удаляя прежнюю. Сотрудник принимает
решение только по заявке в `UNDER_REVIEW` и актуальной оценке. Одобрение с
обязательным ограничением или неполными проверками блокируется. Для отказа
нужна причина; одобрение сохраняет сумму, срок и ставку демо-продукта.

Отправка использует существующий модуль `assess_application`; результат,
снимок входа и версии сохраняются в `assessments` отдельно от редактируемой
анкеты. Демо-симуляторы детерминированы: проверка синтетической компании
возвращает `SYNTHETIC_COMPANY_MATCH`, а кредитная история —
`NO_DEMO_DELINQUENCIES`. Это тестовые данные, не реальные внешние проверки.
Оценка не является итоговым решением сотрудника.

Сотруднические маршруты требуют роль `BANK_EMPLOYEE` из серверной учётной
записи. Черновики не отображаются в очереди и недоступны через карточку/оценки.
Повторное действие или конкурентное решение возвращает **409** и не перезаписывает
результат первого сотрудника.

Все ошибки API имеют форму
`{"error":{"code":"...","message":"...","fields":[]}}`.
401 — вход, 403 — роль, 404 — отсутствующий или чужой объект,
409 — версия/состояние, 422 — поля, 503 — недоступная БД/миграции.
Ответы не содержат пароли, хеши, внутреннюю политику или трассировки БД.

## Условия демопродуктов

Источник: [официальная страница бизнес-кредита Альфа-Банка](https://alfabank.ru/sme/profits/businesscredit/),
проверена 21.10.2026 по доступным данным поискового индекса. На странице указаны
суммы кредита без залога от 300 тыс. до 30 млн рублей и индивидуальное определение
ставки. Это источник ориентира, а не подтверждение персонального предложения.

В демо созданы два учебных варианта: оборотные средства (300 тыс.–5 млн,
6–36 месяцев) и оборудование (300 тыс.–10 млн, 6–60 месяцев).
Суженные диапазоны, сроки, расчётная ставка **24%**, веса и ограничения скоринга —
явные допущения команды. Два варианта не выдаются за отдельные реальные продукты
банка. Ответ API содержит `source_url`, `source_checked_on`, `rate_note`,
`assumptions`, `policy_version`. Существующий пример политики скоринга не изменён;
демопродукты backend имеют собственные версии.

## Локальная разработка и тесты

```sh
cd backend
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements-dev.txt
```

Для запуска самого приложения нужна PostgreSQL. Передайте в окружении
`DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DATABASE`, `JWT_SECRET`
и при необходимости переменные демоданных. Затем:

```sh
.venv/bin/alembic upgrade head
.venv/bin/python -m app.seed
.venv/bin/uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
```

`app.seed` выполняет заполнение только при `SEED_DEMO=true`. При старте приложения
таблицы не создаются автоматически: схемой управляют миграции.

API-тестам нужна отдельная PostgreSQL с `TEST_DATABASE_URL` и именем базы `test_*`.
В ней тесты создают уникальные схемы `test_<uuid>` и удаляют только их.
Не передавайте адрес рабочей БД. Если PostgreSQL/Docker нет, можно поставить
дополнительный пакет с временным PostgreSQL 16.2:

```sh
.venv/bin/python -m pip install --require-hashes -r requirements-postgres-test.txt
.venv/bin/python -m pytest -q
.venv/bin/ruff check app migrations tests/api
```

Дополнительный пакет используется только тестами и не входит в Docker-образ.
Без TEST_DATABASE_URL и пакета pgserver API-тесты будут явно пропущены: такой
запуск нельзя считать проверкой backend. Отдельные тесты скоринга не требуют БД.

Покрыты вход, роли, чужие заявки, защищённые поля, денежные типы, частичные
обновления, конфликты версий, ограничения БД, повторное заполнение, миграции,
совместимость скоринга и сохранение черновика после остановки/нового запуска
отдельного процесса uvicorn. [Схема данных](docs/architecture.md).

Проверка предыдущей версии: 84 теста прошли на Python 3.12.15 и временном PostgreSQL
16.2, включая реальный HTTP и перезапуск процесса.

21.10.2026 дополнительно проверен запущенный через Docker Compose проект:
Python 3.12.15, PostgreSQL 16.13, оба контейнера healthy. Основные файлы приложения
и requirements.txt в контейнере совпали с рабочей копией по SHA-256. Через HTTP
проверены вход клиента и сотрудника, каталог, своя компания, создание и изменение
черновика, отказ без токена, запрет чужого GET/PATCH, запрет подмены статуса и
конфликт устаревшей версии. После перезапуска обоих контейнеров все поля,
revision и даты тестового черновика сохранились точно; проверка прав повторно
прошла. Swagger, OpenAPI и готовность миграций доступны. Полный набор 84 тестов
внутри Docker отдельно не запускался; это проверка работающего Compose-сценария.

Публикация за пределы локального демо требует отдельной настройки TLS,
секретов, ограничения попыток входа и резервного копирования; текущая Compose
конфигурация предназначена для локальной демонстрации.
