# Оценка заявки предпринимателя

Автономный модуль на стандартной библиотеке Python 3.10+. Нет обращений к БД,
сети, системному времени, случайным числам или импорта FastAPI.
Правила демонстрационные: это не кредитная политика Альфа-Банка и не
статистическая вероятность дефолта. Итоговое решение принимает сотрудник.

**Статус контракта: v1 принят при реализации основы backend 21.10.2026.**
Поля черновика, компании и серверной политики совместимы с модулем; маппинг
описан в `backend/README.md` и проверяется интеграционным тестом. Точка входа
объединяет расчёт балла и применение правил в один безопасный вызов.
Вызов при отправке заявки и сохранение оценки ещё не реализованы.

## Быстрая интеграция

При запуске backend из его каталога:

```python
from app.scoring import PolicyValidationError, assess_application

try:
    result = assess_application(input_data, product_policy, checks)
except PolicyValidationError as error:
    # Ошибка настройки backend: не сохранять кредитный отказ.
    # error.errors содержит field, code, message.
    raise
```

Из корня репозитория импорт: `from backend.app.scoring import assess_application`.
Вызов синхронный, результат — обычный JSON-совместимый `dict`. Вход не изменяется.
Служебные функции в `contracts.py`, `scorecard.py`, `policy.py` принимают уже
проверенные данные; backend должен вызывать только `assess_application`.

Готовые данные находятся рядом:

- `examples/request.json` — все три аргумента вызова на синтетической заявке.
- `examples/response.json` — полный фактический результат для этого запроса,
  проверяемый тестом на точное совпадение.
- `examples/demo.py` — одобрение, рассмотрение, отказ, неизвестная проверка,
  пропуск и некорректные данные. Чтение файла есть только в примерах, не в модуле.

Из корня репозитория:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s backend/tests -v
PYTHONDONTWRITEBYTECODE=1 python3 -m backend.app.scoring.examples.demo
```

Тесты совместимы с pytest, но его установка для запуска не нужна.

## Вход: input_data

Все поля обязательны. Отсутствующий ключ и `null` означают пропуск, а не ноль.
Неизвестные ключи отклоняются, чтобы опечатка в имени поля не осталась незамеченной.

| Поле | Тип и смысл |
| --- | --- |
| `schema_version` | Строка `"1.0"` |
| `application_id` | UUID-строка, нормализуется в стандартную запись |
| `application_revision` | Целое 1–2147483647; backend связывает оценку с этой редакцией |
| `as_of_date` | Дата оценки `YYYY-MM-DD` или Python `date`, без времени |
| `product_code` | Непустая строка, совпадает с кодом политики |
| `requested_amount` | Положительная сумма кредита, RUB |
| `term_months` | Целое 1–360, дополнительно проверяются пределы продукта |
| `purpose` | Непустая цель; сохраняется в снимке, не влияет на балл |
| `legal_form` | Непустая форма бизнеса; сохраняется в снимке, не влияет на балл |
| `registration_date` | Дата регистрации, не позже `as_of_date` |
| `average_monthly_revenue` | Среднемесячная выручка, RUB |
| `average_monthly_operating_expenses` | Среднемесячные операционные расходы **без кредитных платежей**, RUB |
| `existing_monthly_debt_payment` | Общая месячная сумма платежей по существующим кредитам, RUB |
| `current_overdue_amount` | Текущая просроченная сумма, RUB |
| `max_overdue_days_12m` | Максимальная длительность просрочки за последние 12 месяцев, целое 0–366 |

Выручка и расходы должны относиться к одному периоду: предлагаем среднее за
последние 12 завершённых месяцев, для молодого бизнеса — за доступные завершённые
месяцы. Подготовка этих средних и проверка периода — ответственность backend.
Если данных нет, передать `null`. Доходы здесь означают выручку, а не прибыль.

Денежные значения: десятичные строки (`"500000.00"`) или Python `Decimal`,
неотрицательные, не более 1 трлн рублей, с точностью до копеек. Значение выше
максимума продукта, но внутри технического диапазона, даёт ограничение продукта;
выход за технический диапазон — ошибка данных. `float`, `int`, `bool`, NaN,
Infinity, экспоненциальная запись в JSON и дробные копейки отклоняются.
Целочисленные поля не принимают строки, `float` или `bool`.
Текстовые поля ограничены 200 символами.

## Вход: product_policy

Все условия передаёт backend из доверенной конфигурации продукта; никаких
скрытых значений по умолчанию нет. Версия должна меняться вместе с условиями.

| Поле | Тип и ограничения |
| --- | --- |
| `policy_version`, `product_code` | Непустые строки до 200 символов |
| `min_amount`, `max_amount` | Денежные значения, `0 < min <= max <= 1 трлн` |
| `min_term_months`, `max_term_months` | Целые 1–360, min <= max |
| `annual_interest_rate` | Строка или Decimal, годовая ставка **в процентах**, 0–100, до 2 знаков; `"24.00"` = 24% |
| `min_business_age_months` | Целое 0–1200 |
| `max_debt_burden` | Строка или Decimal, доля `(0; 1]`, до 2 знаков; `"0.70"` = 70% |
| `max_overdue_days_12m` | Допустимая длительность просрочки, целое 0–366 |
| `approve_score` | Целое 1–100 |
| `review_score` | Целое 0–99, строго меньше approve_score |
| `required_checks` | 1–20 уникальных имён обязательных источников |

Неверная политика, пропущенные поля или несовпадение `product_code` вызывают
`PolicyValidationError`. Это ошибка конфигурации сервера, не отказ клиенту и не
просьба клиенту исправить финансовую анкету. Пример политики в `request.json`
остаётся отдельным тестовым сценарием. Версии демопродуктов backend описаны
в `backend/README.md`; их условия не подменяют этот пример.

## Вход: checks

Список до 20 объектов `{"source": "credit_history", "status": "PASS",
"reason_code": "AVAILABLE"}`. Все три поля обязательны. Имена источников:
латинская строчная буква, далее строчные буквы, цифры или `_`, всего до 64 символов.
Повтор одного источника — ошибка входа. Статусы: `PASS`, `FAIL`, `UNKNOWN`.

- `PASS` — источник получен и соответствующая обязательная проверка пройдена.
- `FAIL` — подтверждённый обязательный запрет. Сбой источника сюда не относится.
- `UNKNOWN` — результат неизвестен; необходимо получить сведения из источника.

`None` и `[]` означают отсутствие проверок. Отсутствующий обязательный источник
равнозначен неизвестному; автоматической рекомендации одобрения не будет.
Дополнительные переданные источники тоже учитываются: их `FAIL` запрещает
одобрение, `UNKNOWN` требует уточнения. Backend должен передавать сюда именно
обязательные проверки, а информационные предупреждения хранить отдельно.
Порядок источников не влияет на ответ.

## Расчёт признаков и балла

Расчёт использует собственный Decimal-контекст с точностью 40 значащих цифр,
независимый от настроек вызывающего кода. Сравнения выполняются до отображения
результата. Деньги в ответе — строки с двумя знаками; отношения — десятичные
строки, без искусственного округления до процентов.

1. Возраст — число полных календарных месяцев к `as_of_date`. Если день месяца
   ещё не наступил, последний месяц не учитывается. Для 29 февраля годовщина
   в невисокосном году наступает 1 марта.
2. Доход после операционных расходов `P = revenue - expenses`.
3. Операционная маржа `M = P / revenue`. При нулевой выручке `null` и 0 баллов.
4. Платёж нового кредита — аннуитет: `A = S * r / (1 - (1 + r)^(-n))`,
   где `r = annual_interest_rate / 1200`, `n = term_months`.
   При нулевой ставке `A = S / n`. Платёж округляется вверх до копейки,
   чтобы не занижать нагрузку. Комиссий, страховок и льготных периодов в MVP нет.
5. Долговая нагрузка `D = (existing_monthly_debt_payment + A) / P`.
   При `P <= 0` отношение `null`, 0 баллов и обязательный запрет.

| Фактор | Условия → баллы |
| --- | --- |
| Возраст, максимум 20 | <6 мес. → 0; 6–11 → 5; 12–23 → 12; >=24 → 20 |
| Маржа, максимум 25 | <=0 или не определена → 0; (0; 0.15) → 8; [0.15; 0.30) → 18; >=0.30 → 25 |
| Нагрузка, максимум 35 | <=0.30 → 35; (0.30; 0.50] → 25; (0.50; 0.70] → 10; >0.70 или не определена → 0 |
| Дисциплина, максимум 20 | Текущая просрочка >0 → 0; иначе история 0 дней → 20; 1–7 → 12; 8–30 → 5; >30 → 0 |

Балл — сумма вкладов, 0–100. Уровень риска: 75–100 `LOW`, 50–74 `MEDIUM`,
0–49 `HIGH`. При невозможности расчёта — `UNKNOWN`. Пороги уровней риска и
таблица баллов относятся к `scoring_version`; пороги рекомендаций относятся
к `policy_version` и могут отличаться. При изменении формул или порядка
применения правил нужно менять `scoring_version`.

## Приоритет правил и объяснения

1. Ошибка настройки политики → `PolicyValidationError`, результата оценки нет.
2. Некорректная или неполная анкета/структура checks → `INSUFFICIENT_DATA`,
   балл `null`, `REQUEST_INFO`, список ошибок. Баллы и запреты по частично
   корректным данным не рассчитываются; после исправления нужен новый вызов.
3. Для корректной анкеты рассчитывается балл. Подтверждённые запреты → `DECLINE`,
   даже при высоком балле и одновременно неизвестных проверках.
4. Если запретов нет, отсутствующие/неизвестные проверки → `REQUEST_INFO`.
5. Иначе балл >= approve_score → `APPROVE`; >= review_score → `REVIEW`;
   ниже review_score → `DECLINE` с причиной `LOW_SCORE`.

Граничные сумма, срок, минимальный возраст, допустимая нагрузка и длительность
просрочки включены в разрешённый диапазон. Любая текущая просрочка >0 запрещена.

Коды обязательных запретов:

| Код | Причина |
| --- | --- |
| `AMOUNT_OUT_OF_RANGE` | Сумма вне условий продукта |
| `TERM_OUT_OF_RANGE` | Срок вне условий продукта |
| `BUSINESS_TOO_YOUNG` | Возраст ниже минимального |
| `NON_POSITIVE_OPERATING_PROFIT` | Выручка не превышает операционные расходы |
| `EXCESSIVE_DEBT_BURDEN` | Нагрузка превышает лимит продукта |
| `CURRENT_OVERDUE` | Есть текущая просрочка |
| `SEVERE_OVERDUE_HISTORY` | Историческая просрочка длиннее допустимой |
| `CHECK_FAILED:<source>` | Получен подтверждённый FAIL источника |

Прочие коды: `MISSING_DATA`, `INVALID_DATA`, `CHECKS_INCOMPLETE`, `LOW_SCORE`,
`SCORE_SUFFICIENT`, `MANUAL_REVIEW`. `reasons` содержит объяснение для каждого
кода. Ошибки полей имеют `field`, `code`, `message`; `code` бывает `MISSING`,
`INVALID`, `UNKNOWN_FIELDS`, `DUPLICATE`, а для несовпадения продукта — `MISMATCH`.

## Результат и обязанности backend

| Поле | Содержимое |
| --- | --- |
| `schema_version`, `scoring_version`, `policy_version` | Версии контракта, расчёта/правил и условий продукта |
| `application_id`, `application_revision`, `as_of_date` | Контекст оценки; при ошибках соответствующих полей может быть null |
| `assessment_status` | `COMPLETED` либо `INSUFFICIENT_DATA` |
| `score`, `risk_level` | Балл и уровень риска; при ошибках null/UNKNOWN |
| `factors` | Код, фактическое значение, points, max_points, explanation каждого фактора |
| `features` | Возраст, доход после расходов, маржа, новый платёж, общий платёж, нагрузка |
| `recommendation` | `APPROVE`, `REVIEW`, `DECLINE`, `REQUEST_INFO` |
| `hard_stops` | Все найденные коды обязательных запретов |
| `reason_codes`, `reasons` | Коды и объяснения рекомендации, включая причины отказа |
| `missing_fields` | Пропущенные поля и неизвестные источники `checks.<source>` |
| `validation_errors` | Ошибки типов, форматов, диапазонов и пропуски |
| `input_snapshot` | Нормализованные input_data, product_policy, checks; null при ошибках данных |

`COMPLETED` означает, что балл рассчитан. При неизвестной внешней проверке
балл может быть рассчитан, а рекомендация — `REQUEST_INFO`. Это не финальный
статус заявки. При невалидном входе backend сохраняет исходную редакцию отдельно:
модуль не пытается сериализовать произвольные некорректные объекты в снимок.

До интеграции участнику backend требуется:

- Поля и период усреднения приняты в основе backend; для этапа отправки
  реализовать получение обязательных проверок и применение серверной политики.
- Передавать доверенные условия, дату оценки и результаты симуляторов;
  не принимать policy/checks/score из клиентской анкеты.
- В одном процессе сохранения связать результат и снимок с актуальной редакцией
  заявки; проверять идемпотентность и конкурентное обновление на своей стороне.
- Отдельно обработать `PolicyValidationError` как техническую ошибку.
- Для `checks.*` получать данные из источника, а не просить клиента менять числа.
- Выбирать публичные поля ответа клиенту; внутренние причины проверок и снимок
  целиком предназначены для backend/сотрудника.
- Сохранять финальное решение сотрудника отдельно от рекомендации.

## Проверки и границы готовности

Набор unittest проверяет четыре рекомендации, JSON-контракт, отсутствие мутаций,
повторяемость при изменении Decimal-контекста, пороги факторов и продукта,
аннуитет и нулевую ставку, пропуски/ошибки, нулевые знаменатели, неизвестные и
неуспешные проверки, а также приоритет обязательных запретов.

- [x] Обработка отсутствующих и некорректных данных.
- [x] Тесты и воспроизводимые примеры интеграции.
- [x] Контракт полей принят для основы backend, совместимость проверена тестом.
- [ ] Подключение к API/БД и проверка сквозного сценария — область backend.
